从零逆向 Aliyun WAF md5__1803

一份可以照着执行的 Python + iv8 纯协议教程：从第一次 HTTP 请求开始，直到业务接口返回 responseHead.code == 0。

目标：browser-free requests + iv8 入口：Lf / LK / Lb 验收：JSON + code 0

先读清楚“纯协议”的含义。 本教程的最终方案不启动 Camoufox、Playwright 或真实浏览器。Python 通过 requests 获取 challenge，iv8 执行 WAF JavaScript，requests 再完成业务回放。这是纯协议实现。它不是“纯算”：纯算还要求完全不执行原始 WAF JavaScript，只用 Python 重写所有算法。
本文用于学习 iv8 API、浏览器 JavaScript runtime 建模和 HTTP 请求回放。请只在有授权的目标上使用，并遵守目标站点服务条款和当地法律法规。

步骤 1

先定义最终成功标准

本步骤目标在逆向之前定义“什么叫成功”，防止被 HTTP 200 或非空签名误导。

目标接口可能返回 HTTP 200 的 WAF HTML。只有以下条件同时满足，才算通过：

challenge_status == 200
replay_status == 200
"application/json" in replay_content_type
responseHead.isSuccess is True
responseHead.code == 0

验收代码应该尽量靠近最终请求，而不是只在 iv8 中检查：

response = session.post(
    signed_url,
    headers=headers,
    data=body_text.encode("utf-8"),
    timeout=30,
)

content_type = response.headers.get("content-type", "")
if response.status_code != 200:
    raise RuntimeError(f"HTTP failed: {response.status_code}")
if "application/json" not in content_type:
    raise RuntimeError("received challenge HTML instead of JSON")

payload = response.json()
head = payload.get("responseHead", {})
if head.get("isSuccess") is not True or head.get("code") != 0:
    raise RuntimeError(f"business failed: {head}")
预期结果你知道最后必须看到 application/json、isSuccess=true 和 code=0，而不是只看到一串 210 字符的签名。
步骤 2

画出三层请求模型

本步骤目标把业务层、WAF challenge 层和最终回放层分开。
业务层JSON body、分页字段、商品筛选条件、业务 headers。
challenge 层HTML、初始化状态、WAF JS、acw_tc。
回放层完整签名 URL、相同 body 字节、同一个 requests Session。

    | POST clear API
    v
HTML challenge + Set-Cookie: acw_tc
    |
    | iv8 page.load + WAF JS
    v
closure LK(url, body, "POST", 2)
    |
    v
https://api.../search/list?md5__1803=...

步骤 8

用 AST 找到真实入口

本步骤目标在不改变原始 bundle 的情况下，静态找出函数源码范围和依赖。

不要一开始就插入 wrapper。先用 Babel parser/traverse 读取 AST：

const TARGETS = new Set([
  "L2", "L3", "L7", "LS", "LU", "Li", "Ln", "LK", "Lf"
]);

traverse(ast, {
  FunctionDeclaration(path) {
    const name = path.node.id && path.node.id.name;
    if (!TARGETS.has(name)) return;

    const deps = new Set();
    path.traverse({
      CallExpression(call) {
        if (call.node.callee.type === "Identifier") {
          deps.add(call.node.callee.name);
        }
      }
    });

    result[name] = {
      start: path.node.start,
      end: path.node.end,
      params: path.node.params.map(p => p.name || null),
      deps: [...deps]
    };
  }
});

每个函数至少记录：

  • 源码起点和终点；
  • 参数数量和语义；
  • 直接调用依赖；
  • 读取的闭包变量；
  • 读取的 window/document/navigator/storage 字段；
  • 返回值是字符串、URL 对象还是副作用。
本案例结果已经确认 Lf -> LK -> Lb，并识别 L3、MD5/LZ 编码和动态随机状态是 LK 的依赖。
步骤 9

恢复 Lf 到 LK 的参数顺序

本步骤目标确认每个参数到底对应 URL、body、method 还是分支标志。

不能看到函数签名就猜：

function LK(a, b, c, d) { ... }

必须找到真实调用点，和一次浏览器成功请求的 URL/body 对照。当前确认调用：

LK(
    requestUrl,
    requestBodyText,
    "POST",
    2
)

第四个参数 2 进入 POST 分支；非 GET/HEAD 的 body 还会参与编码。签名前后的 body 必须保持完全一致：

body_text = json.dumps(body, ensure_ascii=False, separators=(",", ":"))
body_bytes = body_text.encode("utf-8")

# 传给 LK 的就是 body_text
# requests 回放的就是 body_bytes
最常见错误签名时传紧凑 JSON，回放时改用 json=body；这可能改变字段顺序、转义和空格，使签名材料不一致。
步骤 10

解释为什么普通 wrapper 会卡死

本步骤目标区分“算法失败”和“观测注入破坏了 WAF 自校验”。

以下注入看似无害：

window.__wafLK = function () {
    return LK.apply(this, arguments);
};

但它会带来至少三种变化：

  1. 函数源码发生变化，Function.prototype.toString() 返回值变化；
  2. 函数层级和调用栈发生变化；
  3. 导出动作可能改变闭包初始化顺序。
诊断原则如果原始 bundle 能执行，加入一个无关变量或 wrapper 后卡死，先恢复原始 bundle，不要继续修改算法。说明问题在自校验或宿主兼容层。

步骤 12

用 page.load 复原 DOM 和脚本顺序

本步骤目标让 challenge runtime 能看到预期的同源页面、script source 和 location。

先删除会自动执行的脚本，再在 HTML 末尾保留原始 WAF script source：

def make_dom_snapshot(html, inline_source):
    dom = re.sub(
        r"<script\\b[^>]*>[\\s\\S]*?</script>",
        "",
        html,
        flags=re.IGNORECASE,
    )
    return dom.replace(
        "</html>",
        '<!--<script name="aliyunwaf_6a6f5ea8">'
        + inline_source
        + "</script>--></html>",
    )

snapshot = {
    "baseURL": API_URL,
    "html": make_dom_snapshot(challenge_html, INLINE_ORIGINAL),
    "headers": [["content-type", "text/html"]],
}
ctx.eval(
    "window.__iv8__.page.load("
    + json.dumps(snapshot, ensure_ascii=False)
    + ");"
)

随后按已确认顺序执行：

  1. 设置 challenge 响应的 acw_tc；
  2. 执行初始化脚本；
  3. 执行外链 WAF runtime；
  4. 安装源码保护；
  5. 执行内联 WAF closure。
不要重复执行如果 HTML 已经自动执行过初始化脚本，再手动 eval 一次可能产生不同随机状态或重复注册 hook。
步骤 13

处理外链 runtime 的宿主兼容

本步骤目标仅修复已经证明是 iv8 宿主差异的卡死点，不改签名算法输入。

13.1 Zi 源码校验

外链 runtime 会从函数源码计算 Zi。iv8 的函数源码形状和真实浏览器不同，可能导致错误分支。当前版本在测试 harness 中需要固定兼容值：

function u1() {
    return Zi = 632, "5rGzyCeeHxhGk9";
}

13.2 matchMedia 高度循环

wF 会读取类似：

matchMedia("(min-device-height: ...)")

如果 iv8 的媒体查询能力始终返回不符合预期的结果，可能进入同步循环。要先用超时和分段日志证明卡点，再做最小媒体兼容修正。

重要这些是当前 bundle 的 iv8 compatibility patch，不是通用 Aliyun WAF 规则。WAF 版本变化后必须重新确认。

步骤 16

判断哪些 Cookie 应该回放

本步骤目标只把经过实测需要的 Cookie 合并到同一个 Session。

challenge 响应可能带 acw_tc。iv8 执行 WAF 后还可能写入 ssxmod_itna、ssxmod_itna2。本案例实测成功路径是：

def merge_acw_tc(session, cookie_header):
    for item in cookie_header.split(";"):
        if "=" not in item:
            continue
        name, value = item.strip().split("=", 1)
        if name == "acw_tc":
            session.cookies.set(
                name,
                value,
                domain="api.cdfsunrise.com",
                path="/",
            )

不要默认把所有 iv8 Cookie 转发：

  • Cookie 可能属于 iv8 自己的 synthetic runtime 状态；
  • 它可能和服务端 challenge 期望的环境不一致；
  • 多余 Cookie 可能让服务端选择另一条验证分支。
本案例结论不是普适规则其他站点可能确实要求完整 Cookie。必须通过同一 Session、多轮 fresh challenge 对照验证。
步骤 17

用 requests 完成最终 POST

本步骤目标使用生成签名的同一 body 字节、headers 和 Session 回放业务请求。
body_bytes = body_text.encode("utf-8")

response = session.post(
    signed_url,
    headers=HEADERS,
    data=body_bytes,
    timeout=30,
)

print(response.status_code)
print(response.headers.get("content-type"))

特别注意四个“不变”：

  1. URL path 不变；
  2. query 不二次编码；
  3. body 字节不变；
  4. Session 不更换。
典型错误签名是在 iv8 中用紧凑 JSON 生成，回放时使用 json=body；或者把签名 URL 复制到另一个 Session。这两种都可能返回新的 challenge HTML。

print(f"totalCount={payload.get('totalCount')}")
print("response_data=")
print(json.dumps(payload, ensure_ascii=False, indent=2))

if head.get("isSuccess") is not True or head.get("code") != 0:
    raise RuntimeError("business acceptance failed")
本案例实际结果replay_status=200、application/json; charset=utf-8、isSuccess=True、code=0、totalCount=484。
步骤 19

第二轮 fresh challenge 验证

本步骤目标证明不是复用了旧 challenge、旧签名或旧 Cookie。

至少连续运行两次，每次都要：

  • 创建新的 requests.Session；
  • 重新请求 challenge；
  • 重新读取 acw_tc；
  • 重新创建 iv8 JSContext；
  • 重新执行初始化和 WAF bundle；
  • 重新调用 LK；
  • 重新回放业务 POST。
for attempt in range(2):
    session = requests.Session()
    challenge = get_fresh_challenge(session)
    signed = generate_signed_url(challenge.text, ...)
    response = replay(session, signed.url, body_bytes)
    assert response.headers["content-type"].startswith("application/json")
    assert response.json()["responseHead"]["code"] == 0
    print("attempt", attempt + 1, "passed")
一次成功不算稳定一次成功可能只是服务端仍接受旧状态，或者某个 Cookie 恰好没有过期。必须做 fresh-session 重复验证。
步骤 20

逐类排查失败

本步骤目标根据失败发生的层级排查，而不是盲目改签名。
现象说明先查什么
首次不是 HTML challenge没有拿到本轮 challengeAPI path、method、body、Session、页面入口状态
外链执行后卡死多半是宿主兼容或源码自校验Zi、matchMedia、DOM script source、重复初始化
__wafLK undefined导出插入位置或执行脚本错误闭包层级、instrumented source、JS 异常
签名 URL 非空但返回 HTML签名材料或状态不一致bd、body 字节、method、query 编码、acw_tc、UA

20.1 外链 runtime 卡死

按以下顺序加诊断输出：

ctx.eval(page_load)
print("after_page_load")
ctx.eval(initializer)
print("after_initializer")

20.2 签名生成了但 replay 仍是 HTML

  1. 打印 body 的 SHA-256，不打印 body 中的私密值；
  2. 确认传给 LK 的字符串与 requests 的 bytes 一致；
  3. 确认签名 URL没有被 Python 二次拼接；
  4. 只转发实测需要的 Cookie；
  5. 确认 iv8 navigator UA 与 requests User-Agent 一致；
  6. 确认 challenge 和 signed replay 属于同一 Session。
步骤 21

纯协议与纯算的边界

本步骤目标准确描述交付，不把 browser-free runtime 误称为纯 Python 算法。
目标是否完成定义
脱离真实浏览器是不启动 Camoufox、Playwright 或浏览器网络栈
纯协议是requests 获取 challenge，iv8 执行 JS，requests 回放业务 API
纯算否完全不执行原始 WAF JS，仅用 Python 重写 L3、随机和编码

纯算的主要工作不是重写 MD5，而是精确复现：

  • L3() 的环境数组；
  • challenge 初始化状态；
  • 伪随机消耗顺序；
  • 动态 alphabet；
  • URL/body/method 的规范化；
  • 不同 WAF bundle 版本的兼容分支。
实际工程建议：如果目标只是无浏览器调用，requests + iv8 已经是完整纯协议方案；只有部署不能安装 iv8 或必须审计全部算法时，才继续纯算移植。
