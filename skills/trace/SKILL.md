# Trace

## Mission

Turn hostile web clients into stable protocol collectors. Browser tools gather evidence; the final path is raw HTTP plus a narrow local sign, bootstrap, decode, transport, JS, WASM, or native helper only when evidence proves it is necessary.

## Ownership

Use Trace when at least one condition is true:

1. The protection family is unknown and the user supplied a page, API, script, request, cookie, token, response, WASM, packet capture, or HAR for end-to-end recovery.
2. The real path crosses bootstrap state, signing, transport wrapping, response decoding, pagination, verifier state, or session state.
3. The deliverable is explicitly a browser-free collector rather than a single observation artifact.
4. A known JavaScript entry, invocation contract, and fixed browser output need Node.js/VM diagnosis and minimal environment patching.
5. A known request, property, function, cookie, storage, or crypto boundary needs a narrow paste-ready browser Hook.
6. A supplied JavaScript file needs structured Babel AST restoration, reversible passes, or intermediate outputs.
7. Fixed trace evidence proves a signer, decoder, serializer, or request adapter and the user wants Python maintenance, primitive regression, or request glue.
8. A live target needs function/script location, initiator stack, JSVMP behavior, or browser fingerprint evidence before a downstream rebuild can start.

## Intake Dispatch

Choose the narrowest truthful path before choosing a tool or runtime. A saved request, HAR, JS/WASM, cookie/token sample, fixed vector, or response is `artifact-only` unless fresh acceptance is explicitly needed; do not open a browser for ceremony. A bare URL or current-session proof is `live-target`. The same target, environment, and goal is `continuation`; reuse the prior gate and reopen only changed surfaces.

Use these stop/continue checks in order:

| Situation | Next action | Do not claim |
|---|---|---|
| Exact endpoint passes a negative control and the target business oracle | Accept an endpoint-scoped `transport-only` result | page, runtime, pagination, or collector understanding |
| Local replay failed or a broad environment patch is proposed | Replay the untouched saved request, name one `primarySurface`, and escalate one rung | solved signer or browser-only root cause |
| One request is proved but pagination, concurrency, or extra routes are not | Finish one repeated business replay first; add at most one route per experiment | collector completeness |
| Evidence result lacks only the target response fields | Ask only which fields matter | a broad implementation brief or browser startup |

The smallest offline route wins. Before a write, live request, target-code execution, session use, dependency install, or runtime switch, apply `references/provider-work-order.md`.

The final runtime must be browser-free:

1. Prefer a pure Python collector.
2. Keep a small local JS, WASM, bootstrap, iv8, or native transport helper only when a verified Python port would currently add more risk.
3. Never ship browser automation, Playwright, Selenium, CDP page-driving, page-context fetch, a browser profile, or manual cookie collection as the solution or fallback.
4. Provide a PyCharm right-click runnable Python entrypoint, normally project-root `main.py` or `collector/main.py`, with no required terminal arguments.
5. For user-supplied Cookie, Authorization, bearer token, API key, private key/IV, or session secret, keep the generated script's top-level constant empty and request local filling; do not default to PyCharm/OS environment variables or embed real values. Dynamic protocol state must be generated or refreshed in the same session chain.

Hard family markers require at least two independent evidence surfaces before handoff. One status code, one cookie name, one token name, one plausible helper output, or one old case note is not enough. When a proved blocker should move to a focused route or installed specialist, use `references/specialist-handoff-contract.md` to preserve scope, permissions, evidence hashes, fallback route, and acceptance criteria.

A WeChat mini program / WMPF target is not a browser-family target. `wechat-miniapp-reverse` owns `miniapp-reverse-mcp`, the WMPFDebugger lease, and `TARGET_ACTIVE` for AppService/WebView; Trace consumes its saved requests, sources, fixed inputs/outputs, and `handoff.json`, and never calls miniapp request/script/frame/target IDs. When Trace needs more WMPF evidence, return a blocked handoff to that skill instead of opening the target in a CDP browser family.

## Runtime Selection Gate

Before executing any known JavaScript entry, classify the host surface. Treat the task as **complex** when any hard signal is present, or when at least two ordinary signals are present:

- Hard signals: parser/lifecycle order, timers or microtasks, self-issued XHR/fetch with replay, Worker/iframe realms, canvas/WebGL/layout/style, native descriptors or `Function.prototype.toString`, multi-stage challenge/bootstrap state.
- Ordinary signals: `document.cookie` plus storage, several DOM object families, dynamic resources, event listeners, `navigator`/screen fingerprint reads, or more than one environment module group.

If the user explicitly selects iv8, `iv8-web-reverse` owns the runtime task from intake; read it before this Trace gate and do not continue with Node.js/VM, AST, or generic Trace env-patch work. For a complex task without a backend choice, select `iv8` first when the installed capability exists; Trace remains the protocol coordinator and `iv8-web-reverse` supplies the local runtime bridge. Do not spend a Node.js/VM trial round before iv8. If iv8 is unavailable, report the capability gap and stop at a handoff instead of silently falling back to a large Node shim. Use Node.js/VM only for a simple known entry: synchronous invocation, fixed inputs, no lifecycle/network/worker/rendering dependency, and at most one narrow host-surface patch. Reclassify immediately when a simple task shows a second host category or two unchanged diagnosis rounds.

## Intake Gate

Declare one intake mode before deep work:

- `live-target`: a current page or endpoint needs fresh wire and runtime evidence.
- `artifact-only`: saved request, HAR, packet capture, source, JS/WASM, token, cookie, fixed vector, or response sample is enough for the next proof; do not invent live acceptance or runtime provenance.
- `continuation`: same target, session assumptions, tool registry, and delivery goal remain current; reuse the prior gate and reopen only changed evidence surfaces.

**Auto-judge the intake path using signals** (detailed logic in `references/mcp-routing-playbook.md`):

1. HAR/request text/JS/WASM/cookie-token sample/fixed vectors are enough, and fresh live acceptance is not required → `artifact-only`; no browser ceremony.
2. Bare URL, or current page/endpoint/session proof is required → `live-target`.
3. Same target, env, and goal continue → `continuation`; reuse gate; reopen only changed surfaces.

For a fresh live target, follow the browser-family selection rule in `references/startup-triage-playbook.md`: an explicit Edge MCP / js-reverse directive selects the `js-reverse` Edge family; an explicit `chrome-devtools` or Camoufox directive selects that family. With no family specified, use `chrome-devtools` for an ordinary clean baseline, `js-reverse` on one host when DP/initiator work is already required, and Camoufox only for evidenced fingerprint pressure. Preserve one `TARGET_ACTIVE` owner and collect baseline before debugger evidence on that host when supported. Do not put multiple target-active browser families in the same parallel tool batch. Record capability gaps before any sequential handoff; use `references/mcp-routing-playbook.md` when the next owner is unclear.

Use focused profiles only for `artifact-only` or already-proved known-boundary work. If a profile needs fresh interaction with a current target, classify it as `live-target` and apply the paired sequential browser rule.

Before any route writes files, sends live egress, executes target code, uses account/session state, installs dependencies, or switches implementation route, apply `references/provider-work-order.md`.

## Startup Gate

When the user explicitly asks to output only a stage gate, follow `../_shared/js-reverse-workflow.md` Stage-Gate Output and return `MODE`, `OWNER`, `NEXT_GATE`, `REQUIRED_EVIDENCE`, and `DO_NOT_USE` without starting evidence collection or implementation. `skill_checkpoint` field rules are in that file under Checkpoint Fields.

Before deep analysis on a fresh or stale gate, report:

1. `MODE`: `live-target`, `artifact-only`, or `continuation`.
2. `TOOLS`: capability snapshot for required and optional methods, configured browser mode, blockers, and selected fallbacks.
3. `CLASS`: `signer-gated`, `verifier-gated`, `decode-gated`, or `session-gated`; add `transport-gated` when TLS, ALPN, HTTP version, client stack, proxy, or route-local admission blocks application semantics.
4. `DELIVERY_SHAPE`: State the smallest acceptable shape from `evidence`, `local-proof`, `compact-replay`, or `collector`:
   - `evidence`: real request, initiator, state source, mutation point, or precise blocker
   - `local-proof`: fixed vectors, decoded sample, restored source, or callable helper without live egress
   - `compact-replay`: one bounded right-click runnable replay for a proved request
   - `collector`: repeatable browser-free Python collector with bounds
5. `RUNTIME_INTENT`: pure Python, Python plus a narrow JS/WASM/bootstrap/iv8/native helper, Python plus local decoder, or a named blocker.

Use `references/startup-triage-playbook.md` for a fresh or stale live gate. For a named blocker, start at the Quick scenario router in `references/symptom-heuristics.md` and open the matching reference. Consult `references/tool-playbook.md` only when selecting or changing capabilities.

## Focused Profiles

- Browser-hook profile: `references/profiles/browser-hook-snippets/index.md`. Deliver one narrow, reversible Console/Snippets Hook. It is observation only, not entry discovery.
- Static-AST profile: `references/profiles/static-ast/index.md`. Use this first on a supplied JavaScript asset when the obfuscation family is unlabeled and the goal is only to make a signer, serializer, or decoder boundary readable. It never executes the target, keeps the last parseable artifact, and reports structural families plus residue metrics.
- AST profile: `references/profiles/ast-deobfuscate/index.md`. Use this when a known obfuscator family (obfuscator.io, sojson, sojson v7, awsc) must actually be restored rather than merely detected. Preserve the original and run `transform -> generate -> reparse -> validate`; do not use AST work as a substitute for request proof.
- Env-patch profile: `references/profiles/env-patch/index.md`. Follow `Rebuild -> Patch -> Consolidate`; exit to the core loop when bootstrap, session, transport, response, or pagination state remains unresolved.
- Pure-Python rebuild: `references/pure-python-rebuild-playbook.md`. Freeze fixed vectors, port primitives one at a time, prove first divergence, and attach request glue only after parity.

Pick exactly one AST route per asset. Structure-only detection and a conservative rewrite belong to Static-AST; a family-specific restoration pipeline belongs to the AST profile. If Static-AST detection names a supported family and the goal grows into full restoration, hand the same task-local artifact to the AST profile instead of running both pipelines over one input.

## Core Loop

Follow the structured **Phase 0-5 workflow** detailed in `references/workflow-overview.md`:

- **Phase 0**: Fingerprint the target (classify decoy vs real, wrapper vs param, gate type)
- **Phase 1**: Prove the real request (capture, initiator, exact payload)
- **Phase 2**: Isolate moving state (classify each changing part, prove provenance)
- **Phase 3**: Locate canonical mutation point (trace wrappers → helpers → primitives)
- **Phase 4**: Rebuild offline (climb escalation ladder, prove first divergence)
- **Phase 5**: Deliver (prove repeatability, package, apply delivery gate)

### Phase 1: Prove the real request

- Capture one clean business-path request before broad hooks.
- Separate entry page, bootstrap assets, decoys, business APIs, verifier calls, telemetry, downloads, async jobs, WebSocket frames, and pagination pivots.
- Bind URL, method, exact query/body bytes, headers, outbound Cookie header, response shape, redirect chain, initiator, and session state.
- Treat wire egress as authoritative when it differs from intermediate getters, callbacks, or cookie jars.

### Phase 2: Classify moving state

Classify every changing part: timestamp, nonce, signed query/body, rotating header/cookie, wrapper field, cursor, bootstrap artifact, decode key, glyph map, session secret, transport profile, sparse delta, counter, heartbeat, elapsed-time dependency, media key, account context, page exception, or host semantic.

Prove cookie provenance, writer, slot, scope, expiry, refresh path, and first downstream consumer. Never hardcode rotating state before proving the writer.

### Phase 3: Locate the canonical mutation point

Trace in this order: transport wrapper, fetch/XHR/Ajax/interceptor, bootstrap script, exposed helper, WASM export, response-side refresh, serializer, binary envelope, key schedule, or stream state. The canonical mutation point is where the wire-shaped payload actually changes, not where business code creates a placeholder.

Handle observer effect explicitly: if hooks, breakpoints, or monkey patches change behavior, restore a clean baseline and narrow the proof before escalating.

### Phase 4: Rebuild offline

Apply the Runtime Selection Gate before choosing an execution host, then escalate one rung at a time:

1. untouched saved-request replay and exact request diff
2. fixed-input parity
3. pure Python primitive or decoder
4. simple known-entry Node.js/VM helper only when the task remains below the complex threshold
5. complex browser-semantic local bootstrap in iv8, or a narrow JS/WASM helper when iv8 is not needed
6. route-local native transport adapter only after repeated packet evidence proves backend expressiveness gaps

Name the primary failure surface before patching: `egress-environment` -> `transport-admission` -> `session-chain` -> `request-contract` -> `signer-confidence` or `verifier-sidecar` -> `business-oracle`. Stop at the first proven divergence and change one owning layer per experiment. A changed exit, token shape, helper load, or HTTP 200 is not a solved oracle.

Before widening runtime, patch surface, transport profile, or route set, record the last proved artifact, exact blind spot, why the next rung is smallest, and how browser-free delivery remains intact.

When one local helper serves more than one request or step, treat process/VM/context identity and hidden mutable state as moving parts. Run the minimal continuity matrix in `references/runtime-state-continuity-playbook.md` before adding host APIs: one persistent world, one fresh world, and one explicit-state ablation with other inputs held constant. If the persistent world self-invalidates after the first call, isolate or port that call instead of paging with the burned instance.

### Phase 5: Prove repeatability and deliver

- Verify helpers and decoders against fixed-input or fixed-payload vectors and keep one negative control.
- Prove one fresh single-page replay on one coherent session chain before scaling, shrinking runtime, pagination, concurrency, or export automation. Treat page/list/detail/download/export as separate contracts until sibling-route evidence proves reuse.
- Require repeated live replay when live replay is authorized. Non-empty signs, plausible token length, helper load success, one HTTP `200`, current cookie jar, or expired browser export are not acceptance.
- For verifier-gated flows, prove sidecars, shared-state consistency, actual request timing, final verifier semantics, and the first downstream consumer. When failures persist after the transcript looks structurally plausible, use `references/verifier-error-localization-playbook.md`; when browser or human oracle samples are involved, grade them with `references/positive-sample-hygiene-playbook.md` before drawing algorithm conclusions.
